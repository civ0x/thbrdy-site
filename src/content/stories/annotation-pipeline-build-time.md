## Project orientation

thbrdy.dev is my personal site — a static Astro app with React islands for the interactive essay diagrams. It deploys on Cloudflare Pages and auto-builds on push to main. The whole thing is built through an agent-driven workflow: I plan changes in one Cowork session, and an executing agent (a separate Claude Code session) reads three files and runs the change autonomously.

## Opener

"The essays are dense — they reference academic papers, domain-specific vocabulary, and external resources a reader may not know. I wanted hover-tap inline annotations on terms, references, and links. The interesting design question wasn't the UI; it was *where the LLM lives in the pipeline*. The decision was build-time, not runtime. Author writes the reference metadata into a per-essay YAML file. An agent at authoring time generates the summary and contextual notes. The author reviews and edits. The annotation ships as static data, alongside the MDX. No runtime API calls."

## Punchline

Model placement is a runtime-properties question first. Once "static, reviewable, zero-latency, zero-runtime-spend" is the right answer for a use case, you don't need a model — you need an agent at build time and a static asset at runtime.

## Arc beats

- Context: essays in the site are dense and benefit from inline definitional and reference popovers (`DECISIONS.md` #018, 2026-02-24). The annotation content needed three modes: term definitions (author-written), reference summaries (would-be-AI-generated), enriched external links (author-curated).
- Constraint stack: (a) static site on Cloudflare Pages — no server-side runtime by default; (b) reader privacy — no telemetry, no third-party calls per hover; (c) author control — every annotation visible to the author before it ships; (d) zero latency on hover — the popover has to render instantly with no spinner.
- Options for the reference-summary mode: cloud LLM call at request time (cached); cloud LLM call at build time, cached in the build artifact; offline agent-generated summary stored in a companion YAML, author-reviewed.
- Choice: offline agent-generated, author-reviewed, stored as static YAML. The workflow is: author adds reference metadata to YAML → agent generates summary and context fields → author reviews/edits → ships as static data.
- Tradeoffs / where the abstraction leaks: regeneration is manual (changing a citation context means re-running the agent); the author becomes the eval rig (subject-matter review is the quality gate); the annotation YAML is a versioned artifact in the repo, which is good for audit and bad for any future "live update" requirement.
- Why this is the right shape for this product: every annotation is *visible and editable* before shipping. No runtime drift. No reader privacy surface. Hover latency is bounded by DOM, not network. The agent's role is generation, not arbitration.
- Lesson: model placement is a runtime-property decision first (privacy, latency, verifiability, cost), capability decision second. Build-time agentic generation is an underrated tier — fits cleanly when the artifact is small, the reviewer is the author, and runtime determinism matters.
